# Decisions

Decisions made where SPEC.md was silent. Newest at the bottom.

## M1 — core engine

- **Instants** are ISO-8601 UTC strings (`toISOString()` form); inputs also accept epoch ms or `Date` (`InstantLike`). Local dates are `'YYYY-MM-DD'` strings, so calendar arithmetic is zone-free.
- **DST disambiguation** in `zonedTimeToUtc` follows Temporal's `'compatible'` mode: a repeated wall time (fall back) resolves to the first occurrence; a skipped wall time (spring forward) is shifted forward by the gap (02:30 → 03:30 EDT).
- **Sunrise** uses the NOAA solar-calculator equations (zenith 90.833°, two-pass refinement). `sunriseUtc(date, …)` treats `date` as the calendar date at that longitude, so far-east longitudes yield an instant on the previous UTC date. San José expected values in tests could not be fetched from a live table in the build sandbox; they were cross-checked against an independent implementation of the simplified sunrise equation (agreement < 1 min). New York values match the widely published 05:25 EDT / 07:16 EST.
- **Custom wake window** whose end is not after its start crosses midnight; `dawnWindowFor` checks today's and yesterday's windows and returns the window's date, which becomes the completion's local date.
- **`EngineEnv`** (`{ game, ctx, levelReachedOn? }`) is the single input for rules needing a game + player. `GameDef` (pillars, quests, ramp stages with per-quest overrides, achievements, optional bonus XP) is the data shape any game supplies.
- **Unlock dates**: `ramp_stage` → Monday of the first week in that stage; `min_level` → `levelReachedOn(level)` if the caller has history, otherwise the join date when the current level already qualifies (else locked); `all` = latest, `any` = earliest. Unlocked pillars are derived from unlocked quests (no separate pillar list per stage).
- **Ramp overrides**: `perWeek` replaces a weekly quota; `targets` replace numeric ProofSpec fields (e.g. `targetPages`). The stage of a week comes from its week index.
- **Counting**: weekly counted completions exclude `isRepair` rows (a repair restores a streak, it does not add weekly progress); daily quests count distinct local dates. Completions on paused days still count (capped by `min(completions, due)`).
- **Full Set day**: every daily quest active that day was done that day, and every weekly-quota quest whose quota was still open at the start of that day was also done that day. Needs at least one due quest; paused days never qualify.
- **Balance flags** use raw completions per pillar and require every pillar of the game (Balanced Week) or of the world (Inner/Outer Balance) to be unlocked that week; skipped weeks (due = 0) earn nothing.
- **Tiers** are compared as exact fractions (`4·done ≥ 3·due`, etc.), so float rounding can never move a boundary. `applyChisel` enforces ≤ 5 per week and ≤ 120 total.
- **closeWeek** is keyed by `userId|gameId|weekStart` (the DB unique key includes `game_id`) and refuses to run before next Monday 00:00 local. The store interface is sync; the DB unique constraint is the real guard in M3/M6.
- **Streaks**: completed and repaired days add 1. Paused and frozen days add 1 only to a live streak (they never start one). Freezes are per player (2 per local calendar month), consumed only when a missed day would break a live streak; one freeze covers that date for every daily quest (matches `streak_freezes(user_id, month, used_on)`). A repair token is an `isRepair` completion on a date where the quest was completed at least twice; each token repairs one missed day within the next 2 dates. Today never breaks a streak. While a missed day is still repairable the streak shows as broken plus `repairableDate`.
- **Perfect Week streak**: skipped weeks bridge; a gap in closed weeks breaks it.
- **Achievements**: added a generic `count_in_week { questId, atLeast }` rule (needed for "5 dawns in one week"). Stats are monotonic "best so far" values (longest streak, longest on-target run, longest absence, most misses before a completion) so unlocking is idempotent and order-independent. "Missed opportunities" = active (unlocked, non-paused) days without that quest. A locked week breaks an on-target run; a week with due = 0 bridges it. World-on-target requires all four pillars of the world unlocked.
- **Proof**: character limits count Unicode code points after trimming; "one line" rejects `\r`, `\n`, U+2028, U+2029. Timer accepts `seconds ≥ minSeconds` or a 3–200 char reflection. Photos are optional string refs.
- **Ledger**: transaction id is derived from the idempotency key (`txn:<key>`) to keep the core deterministic; reusing a key with different entries throws. Zero-amount entries are rejected; currency is upper-cased and must be 3 letters.
- **Event bus**: named handlers; the bus skips a handler that already processed an event id (handlers must still be idempotent across processes); a failing handler does not block others and can be retried by re-emitting.
- `tsconfig.core.json` already includes `src/games`, `src/sculpture`, `src/share` for later milestones. A typed test fixture game lives in `src/core/testing/` (not exported from the barrel).

## M2 — Game 1 config

- **GameDef additions** (generic, optional): `worlds` (name/description per world), `books` (`{ questId, pagesField, bookIdField, finishedXp }`) and `eventDecorations` (`perfect_week → gold_vein`, `balanced_week → plinth_carving`, `book_finished → laurel_leaf`). Core `books.ts` adds pages and reports `finishedNow` exactly once.
- **Founding** is the `founding: true` flag; the ★ is never part of a title. Pillar `covers` text is copied verbatim from §6.1 (with its trailing period).
- **Ramp**: unlocks come from each quest's `unlock: ramp_stage` rule; stages only override targets. The apprentice stage restates `read targetPages 10` explicitly (as in §6.3). Adept restates `stillness 5`.
- **Early Riser** uses the new `count_in_week { questId: 'g1.dawn', atLeast: 5 }` rule (raw dawn completions in one Monday-week).
- **Duplicate decorations**: Finisher, The Full Protocol and Well-Rounded list the same decoration their triggering event already awards every time (laurel_leaf, gold_vein, plinth_carving). The first event's decoration is treated as the achievement's, so it is not added twice. Other achievement decorations (plinth symbols, rings) are added once when earned.
- **Achievement XP** is not specified, so achievements award no XP yet (the `achievement` XP source and key helper exist).
- **`validateGameConfig`** lives in `src/core/validate.ts` (engine-level; any game). Ramp target overrides are limited to known numeric proof fields per proof type (reading `targetPages`, duration `minMinutes`, timer `minSeconds`, journal `minWords`, text `minChars`/`maxChars`).
- **Simulator** (`src/games/simulator.ts`) is generic (any GameDef), deterministic and in-memory. It validates every check-in through `validateCheckIn`, awards quest XP, feeds books (auto-creates a new book when one is finished; default 200 pages), closes weeks after each Sunday through the idempotent `closeWeek`, applies `applyChisel`, adds bonus XP and decorations, and evaluates achievements at the end of each day. Default check-in time is 08:00 local (dawn 05:00).
- **Core tests keep the fixture game** (`src/core/testing/fixtureGame.ts`) so the engine stays game-independent; Game 1 behaviour is covered by `src/games/game1/*.test.ts`.
- **Seed** (`scripts/gen-seed.ts` → `supabase/seed.sql`, built by pure `src/games/seedSql.ts`): game slug = game id (`'g1'`); `games.config` holds the game minus quests/achievements (those get their own rows); quests keyed by `(game_id, key)` with `sort_order` = config order; achievement `key` = config id (e.g. `bookworm`). The `window` column is quoted (`"window"` is reserved in Postgres). Plans `free` and `pro` with entitlement `statue_rerolls` = 1 (free) / 5 (pro; spec says only "more with Pro").
- **M3 schema requirements implied by the seed**: `plans(key unique, name, description)`, `entitlements unique (plan_id, feature_key)`, `games.slug unique`, `quests unique (game_id, key)`, `achievements.key unique`.

## M3 — Database

- **Migrations** `0001`–`0010` in `supabase/migrations/`: foundation helpers, profiles/billing, games catalog, player progress, sculpture, sharing, ledger, Phase 2 seams + analytics, signup trigger, RLS/grants. They assume Supabase's `auth.users`, `auth.uid()` and roles `anon`/`authenticated`/`service_role`.
- **Account deletion vs append-only**: profile-owned data cascades from `profiles` (which cascades from `auth.users`). The append-only trigger on `xp_events`, `chisel_events` and `reputation_events` therefore allows a DELETE only when it comes from a foreign-key cascade (detected with `pg_trigger_depth() > 1`, since cascades run inside Postgres' RI trigger). Direct UPDATE/DELETE/TRUNCATE by any role, including `service_role`, is rejected. Ledger tables have no such exception: `ledger_accounts.owner_id` is polymorphic (no FK to profiles), entries/transactions use `on delete restrict`, and `payouts.user_id` is `on delete restrict` (money history outlives accounts). `ledger_transactions` is also append-only.
- **Ledger check**: deferred constraint triggers on `ledger_entries` and `ledger_transactions` insert verify at commit that each transaction has ≥ 2 entries, a single currency (via the accounts) and sums to 0. Zero-amount entries are rejected by a check.
- **Sculpture**: `seed` is 0..2^32−1 (the sculpture RNG is 32-bit). Checks tie `status = 'complete'` ⇔ `pieces_revealed = 120` ⇔ `completed_at is not null`. `archetype` defaults to `philosopher` (the player picks during onboarding; the row exists from signup). The chisel trigger caps at 120; once complete a new rock may be started (partial unique index allows one non-complete sculpture per user).
- **Signup trigger** (`handle_new_profile`, security definer) creates the sealed sculpture and, if a game with slug `g1` exists, the enrollment. If Game 1 is not seeded yet, enrollment is skipped silently; `seed.sql` backfills enrollments for every existing profile (idempotent), so order of operations does not matter.
- **Who writes what (RLS)**: players (`authenticated`) read their own rows. They write directly only: their own profile (insert/update limited by column grants — never `role`, `status` or `joined_at`), paused days, books (add/rename/remove; `pages_read`/`finished_at` only via the server) and shares. Completions, takeaways, journal entries, XP, streak freezes, week results, chisel events, decorations, achievements, enrollments, subscriptions and ledger rows are written by route handlers with the service role, because proof validation and scoring live in the core. Players may delete their own journal entries.
- **Grants**: the RLS migration revokes Supabase's default blanket grants from `anon`/`authenticated` and grants only what the policies need. Catalog tables (`games`, `quests`, `achievements`, `plans`, `entitlements`, `seasons`) are readable by `anon` and `authenticated`, writable by admins via `is_admin()` (security definer, avoids recursive RLS on profiles). Admins get no special access to journal entries.
- **Public shares**: `get_public_share(slug)` (security definer, granted to `anon`/`authenticated`) returns only rendered fields plus the owner's handle/display name, excludes deleted shares and suspended/deleted owners, and strips journal items from `item_refs` unless `include_journal` is true (object keys `journal`/`journal_text`, or array elements with `"type": "journal"`). It never touches `journal_entries`.
- **Other constraints added**: `week_results`/`chisel_events` `week_start` must be a Monday; `week_results.pieces ∈ {0,1,2,5}` and `done ≤ due`; `streak_freezes` unique per (user, used_on) with `month` matching `used_on`; takeaways 10–200 chars with no line breaks; `profiles.handle` is nullable (row can exist before onboarding finishes) but unique and `[a-z0-9_]{3,30}`; face photo requires `face_consent_at`.
- **Phase 2 seam columns** (`payouts`, `kyc_records`, `reputation_events`, `fraud_flags`) were designed here (no blueprint columns were available): payouts carry amount/currency/rail/status/ledger_transaction_id; KYC provider/status; reputation kind/delta/source; fraud reason/severity/status.
- **test-db.sh**: binaries from `PG_BIN`, else `pg_config --bindir`, else `/usr/lib/postgresql/16/bin`. Postgres refuses to run as root, so when `id -u` is 0 the server commands (`initdb`, `pg_ctl`) run as the `postgres` OS user via `runuser` (or `sudo -u`), with the temp dir chowned to it; `psql` connects over TCP to 127.0.0.1 with trust auth as DB superuser `postgres`. On a normal Mac no user switching happens (bash 3.2-safe). Free port = random probe with `/dev/tcp`. Cleanup on EXIT stops the server and removes the temp dir. The unbalanced-ledger test intentionally lets one COMMIT fail (`\set ON_ERROR_STOP 0` for that statement) and then asserts nothing was persisted.

## M4 — Sculpture

- **Frame**: every sculpture uses a 600×800 canvas; AI statue images must use the same frame so shards and decorations line up. `STATUE_BBOX` is x 150–450, y 30–762 (plinth base on the ground line y 762, rock ground y 764). Light comes from the upper left everywhere (rock facets, statue shading, shadows cast to the lower right).
- **Rock hugs the statue**: the rock is not a free-form blob. `STATUE_PROFILE` is a convex hexagon containing every archetype (head, raised arm, shield, spear tip, plinth). The outline walks the profile clockwise and pushes every vertex outward past its edge's line (4–42 px, with shallow notches), so the block provably contains the profile (hence any archetype) while staying tight. Seeds vary per-edge bulge, vertex count and notches. The base is flat on the ground.
- **Rock look**: 8–11 large planes are Voronoi cells computed in a squashed, sheared space (tall, slanted planes like split stone). Each plane gets a normal biased away from the viewer toward the block's edges; Lambert shading against the key light sets its tone. Edges are bevelled (highlight where an edge faces the light, crease where it faces away). Plus fine smooth veins with branches, 3–5 shaded chips at the rim, 6–12 surface cracks, grain/mottle noise, an inner rim shadow on the lower-right edges and a soft ground shadow cast to the right. Shard seams are drawn very faintly (hint of the pieces, not a net).
- **Face last**: exactly `HEAD_SITES = 10` shard sites go to the head band: one always sits just under the chin, the other nine are spread above y 124; body sites stay below y 214. The head/body seam therefore falls below the beard, so the last 10 pieces cover the whole head (tested by sampling the head ellipse and the beard tip). `Shard.head` marks these; the reveal order puts them last, farthest-from-face first. The head region used in the tests is the top 17% of the statue box (spec says "~15%"; 15% would cut through the beard in this frame).
- **Reveal order**: body shards bottom-up by centroid y with ±18 px seeded jitter (plinth first).
- **Cracks on deck**: `crackIntensity = min(1, pct/0.75)`; per on-deck shard `ceil(intensity × 4)` crack lines, generated from a fixed per-shard sequence so more progress only adds lines. On-deck shards also get a darker loosened edge and a slight shade; at intensity 1 their edges glow gold. Purely visual.
- **Rough cut**: the 10 most recently revealed shards show the rough-cut image (placeholder: the silhouette thickened, flat-planed, with point-chisel marks); the complete statue shows none.
- **Placeholder statue / archetypes**: `renderSculptureSvg` takes an optional `archetype` (default `philosopher`) used only when no images are passed. Philosopher: bearded, chiton with pinned sleeve, himation over the shoulder with folds and a cascade, scroll at the chest. Athlete: heroic torso, hip drape, contrapposto legs. Warrior: shield, spear, Corinthian helmet pushed up. Orator: draped, clean-shaven, raised arm. The head is drawn in its own frame and scaled 1.16× about the crown; its silhouette paths are transformed numerically so clipping matches. `Archetype` lives in `placeholderStatue.ts` (re-exported by the barrel); `PlaceholderStatueProvider` returns data-URL SVGs for the chosen archetype.
- **Decorations** (by count): `laurel_leaf` ×4 leaves each (max 24) on two branches along the hairline; `gold_vein` up to 10 kintsugi-like seams clipped to the figure (not the plinth); `plinth_carving` 1 = meander on the plinth face, 2+ = also on the base; `plinth_symbol_<pillar>` one symbol per pillar on the plinth face; `inner_ring` / `outer_ring` glowing ellipses around the plinth base, drawn half behind and half in front of the statue. Decorations are clipped to revealed shards until the statue is complete.
- **Previews**: `scripts/render-previews.ts` renders with Playwright's Chromium (sharp fallback for single SVGs). Besides §8.4 it writes `sculpture-seed1-60-week100.png`, the `sculpture-progression.png` contact sheet (0 → 120) and `statue-archetypes.png`. The intermediate `previews/*.svg` files are git-ignored.

## M5 — Share cards

- **Model builder** (`src/share/model.ts`) was already in place: per-scope allowed item types and counts (`SCOPE_ITEMS`), ticked-item filtering, journal stripping via `includeJournal === true`, public-text filter on takeaway/journal/stat text, handle validation, card pillar derived when all items share one. Ticked items of a type the scope doesn't accept are **dropped**, not errors — a card fails only when fewer than `min` valid items remain.
- **Cards** (`src/share/cards.ts`): `renderShareCardSvg(model, { variant: 'light' | 'dark' })` → 1200×630 SVG. Marble field (two `feTurbulence` layers + vignette), Greek-key border on all four sides with gold diamond corner ornaments, inner hairline frame, Cinzel wordmark "GAMIFY THE GRIND" with divider, footer inside the inner frame: `@handle`, "SET IN STONE" tagline, pillar emblem + name (emblems reused from `src/sculpture/symbols.ts`). Pillar display names duplicated in `PILLAR_NAMES` (share must stay game-agnostic; the eight ids are a fixed core type).
- **Text layout** is hand-rolled: `wrapText` uses a per-class advance-width estimate (caps 0.72×, lowercase 0.52×, narrow glyphs 0.28×, spaces 0.3×) since the core can't measure fonts; `ellipsize` truncates at word boundaries. Dates format from the `LocalDate` string with a fixed month table (no `Date` needed).
- **Milestone cards embed the real sculpture**: `renderSculptureSvg` output nested in the card, clipped to a waist-up crop (`STATUE_BBOX` top 420px) in a framed right-side panel — matches the "share cards default to a bust crop" rule. Only shown when `piecesRevealed > 0`. Every milestone also gets a 120-piece progress bar with quarter ticks.
- **Achievement cards**: star medallion for `inner`/`outer`/`all` scopes, pillar emblem otherwise; laurel wreath = stem arc + pointed-leaf path rotated radially toward each tip; rarity colors common→legendary (grey, green, blue, purple, gold).
- **X intent** (`src/share/intent.ts`): `postLength` counts code points with every `https?://` URL weighted as `POST_URL_WEIGHT = 23`. `xIntentUrl({text, url})` encodes via `URLSearchParams` and trims the text (`fitPostText`, word-boundary cut + '…') so text + attached URL never exceeds 280 — a share action should never produce a post X would reject. `suggestedPostText` reserves the 23-char URL slot and appends `#GamifyTheGrind` only when it fits.
- Share XP stayed in core (`shareXpEvent`, +5 once per local day); nothing share-related reads the clock.

## M6 — Next.js app layer

- **Supabase wiring** follows the `@supabase/ssr` cookie-adapter pattern: `createClient()` async factory in `src/lib/supabase/server.ts` reads cookies via `next/headers` (cookie `set` failures inside Server Components are swallowed — middleware refreshes tokens), `client.ts` is a `createBrowserClient`, `admin.ts` is a plain service-role `createClient` used only inside route handlers, and `middleware.ts` refreshes the session then gates every non-public path to `/login?next=…` (`/s/*`, the share image, Stripe webhook, cron and `/auth/*` stay public).
- **Pages are thin loaders**: `requireViewer` (in `src/lib/viewer.ts`) returns `{supabase, user, profile}` and bounces anonymous users to `/login` and handle-less users to `/onboarding`; each page then calls repos/core directly and passes plain data to components. Everything player-scoped is `force-dynamic`.
- **Repos** (`src/lib/repos/`) are pure row↔core mappers + loaders that take whichever `SupabaseClient` the caller picks (user session for page reads, service role for route writes). Quests are stored by uuid but keyed by `key` for the engine (`questKeyByUuid`), same for achievements.
- **Check-ins** run through the core event bus (`src/lib/checkin.ts`): `validateCheckIn` → insert `completions` → `quest.completed` fans out to handlers for XP (quest + full-set bonus), records (takeaway / encrypted journal / book page advance → `book.finished` → +150 XP + laurel), streak freezes, and achievement evaluation. Unique constraints and XP idempotency keys make every side effect retry-safe; journal text never touches `completions.payload`.
- **Week close** (`src/lib/weekClose.ts`) closes the *just-ended* Monday-week: `computeWeekResult` → `week_results` (the unique `(user_id, game_id, week_start)` insert is the idempotency guard) → `chisel_events` (the M3 trigger advances the sculpture) → bonus XP → perfect/balanced decorations → achievement re-evaluation. The cron route calls it hourly per enrolled player; a player's week is skipped until their local Monday 00:00 has passed.
- **Shares are re-derived server-side**: `src/lib/shareItems.ts` builds the eligible card items from the player's own rows (takeaways, completions, pillar lines, decrypted journals, week results, earned achievements, milestone moments from the sculpture row). `/api/shares` accepts only `{scope, itemIds}` — the client can pick, but can't fabricate card content. Journal candidates carry the decrypted text so the preview is honest; they still only publish when `include_journal` is ticked.
- **Journal crypto**: AES-256-GCM via Web Crypto (works in Node route handlers and edge); 32-byte base64 `JOURNAL_ENCRYPTION_KEY`, random 12-byte nonce per entry, stored as Postgres `bytea` hex (`\x…`).
- **Milestone item** `decorations` widened from `string[]` to `DecorationInput[]` so counted decorations (`{type, count}`) survive the card model — matching what `renderSculptureSvg` accepts.
- **Onboarding** is a 5-step client form (name → place → face → archetype → vision). Profile fields write through the user's own session (they're the column-granted writable set); the archetype goes through `POST /api/sculpture` because sculpture rows are service-writes. The "vision" moment renders the player's *real* sculpture seed at 120 pieces. Referral links land as `/onboarding?ref=<slug>` → `POST /api/referrals`.
- **Admin** is a skeleton catalog editor (quest title/XP inline, read-only achievement list) gated on `profiles.role = 'admin'` — catalog writes go through the admin RLS policy.
- **Stripe webhook** verifies `stripe-signature`, syncs `subscriptions` on `customer.subscription.*` (upsert by `stripe_subscription_id`, user via `metadata.user_id`), and ignores non-Pro price ids. No checkout UI yet.
- **Share image route** serves the card as `image/svg+xml` (allowed by spec); swap for `next/og` ImageResponse if a crawler ever needs raster. `/s/[slug]` re-uses `get_public_share` (anon role) and renders the stored `item_refs` through the same model builder.
- **Wellness wheel + temple header** are hand-rolled SVG (no chart lib); a pillar's temple column lights when every quest under it is `onTarget` for the week.

## M6 restructure — multi-game app (owner request)

- **`/home` is a lobby, not Game 1's board.** Enrolled games show as cards with today's progress and week %; unenrolled active games show under "Discover" with an Enter button. Global XP/level and the account sculpture stay on the lobby — one marble no matter how many games run.
- **Game area routes** are `/games/[slug]` (board + wheel) and `/games/[slug]/quest/[questId]` (check-in). The old flat `/quest/[questId]` was deleted — quest keys are only unique per game, and the page needs game context anyway.
- **`loadEngineState` now requires the slug** and filters loaded completions to the game's quest ids, so other games' completions can't pollute streaks, stats or week results. `acceptCheckIn` takes `gameSlug` and rejects non-enrolled check-ins; `POST /api/checkins` requires `{gameSlug, questKey, payload}`.
- **`POST /api/enroll`** (join → `state='active'`, idempotent upsert) and **DELETE** (leave → `state='left'`; history kept). Enrollments remain service-writes.
- **Cron iterates every active game** and calls `closeLatestWeek` per (player, game); week results/chisel events stay per-game rows.
- **Share candidates span all enrolled games**: quest/pillar/day/week/achievement items are collected per game via `loadEnrolledStates`; the day card merges every game's today board (full-set requires all games' boards done); milestones, takeaways, stats and journals stay account-level. Item ids carry the game slug where needed (`week:g1:2026-09-29`).
- **Achievements page** groups by game title; **admin** picks a game via `?game=<slug>`.
- **Sculpture cracks** on `/sculpture` use the best current-week completion pct across enrolled games (any game can feed the marble).

## Sculpture ownership (owner correction)

- **Only the founding protocol carves the marble.** `GameDef.feedsSculpture` (persisted in `games.config`) marks whose week-close may emit `chisel_events`, store `week_results.pieces > 0`, and write `sculpture_decorations` (check-in achievements, book-finish laurels). `game1` sets it; other games never touch the statue even if enrolled. The sculpture stays account-level — it just answers to one game.
- `/sculpture` on-deck cracks use only sculpture-feeding games' current week; week cards and `piecesChiseled` report 0 for non-feeding games so share cards can't imply a game chiseled when it didn't.

## Lobby experience pass (owner request — "make home an experience")

- **3D museum hero on `/home`.** `src/lib/three/sculptureScene.ts` ports the docs/chisel-3d-demo prototype to modern three (ESM addons, physical light units, CapsuleGeometry), seeded by `sculptures.seed` so the rock matches the account. Loaded client-only via `next/dynamic` — three.js stays out of the server graph and first-load JS; the flat `StatueSvg` renders underneath as the loading/no-WebGL fallback (WebGL-context failure degrades silently).
- **Chisel Day replays live.** If the newest `chisel_events` row is <36h old, the hero mounts at `pieces_revealed - n` and animates those n chunks falling after a short delay — coming back Monday, you watch your week land.
- **Ambient layer is zero-dep DOM/CSS:** drifting dust motes (2D canvas, 42 particles, pauses when hidden), film grain (SVG turbulence + steps()), `Reveal` (IntersectionObserver rise-in), `TiltCard` (pointer-driven perspective + gold sheen), `CountUp` (ease-out counters), `text-shimmer` heading, `.fill-bar` week bars that fill when scrolled into view. No GSAP/Lenis — the lobby needs atmosphere, not scrollytelling; those stay on the table for the landing page.
- **`prefers-reduced-motion` honored everywhere:** no auto-rotate, dust, grain jitter, reveals, tilt, or count animation; the chisel replay places instantly.
- **`/preview` is a dev-only mock of the lobby** (404s in production, middleware-public) so the experience is reviewable without Supabase.
